# 변경 관리와 검증 절차

## 작업 시작부터 완료까지

1. 요청을 PRODUCT_PLAN의 ID에 연결하고 현재 동작/원하는 동작/인수조건을 적는다.
2. 설계 변경이 필요하면 CHANGELOG에 결정·이유·대안·영향을 먼저 기록한다. API/DB/화면/분석 의미가 바뀌면 CONTRACTS와 DATA_DICTIONARY를 먼저 갱신한다.
3. 경로·payload·상태·단위·출처·호환성·실패/취소/중복/재시도 조건을 확정한 뒤 코드 변경을 시작한다. 외부 자격증명이나 실제 기기가 필요하면 구현과 실제 검증 범위를 나눈다.
4. 작은 단위로 구현한다. 같은 파일을 여러 작업자가 동시에 바꾸지 않도록 담당 파일을 정하고 통합자는 공통 라우트/스키마/요약을 조립한다.
5. 임시 DB에서 관련 API/회귀·브라우저 테스트를 수행한다. 마이그레이션은 기존 v1 DB 보존/재시작/빈 DB/명시적 reset도 검사한다.
6. 변수 목록을 재생성하고 문서/계약/테스트 연결과 diff를 확인한다. 완료/실패/미실행/자격증명·기기 대기를 분리해 CHANGELOG에 기록한다.
7. 배포 전 무료 서버의 DB 유실 가능성과 내보내기 한계를 확인한다. 변경이 Git에 저장된 상태와 실제 공개 배포 버전을 구별한다. 공개 검증은 GET 먼저, 필요한 쓰기는 본인이 만든 임시 자료만 정리한다.

저장소 CI는 `npm run docs:check`, `npm test`, 기존 및 자동화 브라우저 검사를 수행하도록 구성한다. 변수 목록이 오래되면 실패한다. 기획·의료적 의미의 일치와 실제 기기 검증은 CI만으로 증명할 수 없으므로 PR 양식의 요구사항/계약/검증/배포 기록으로 함께 검토한다.

## 기획 변경 기록 양식

`변경ID / 날짜 / 관련요구ID / 변경 전·후 / 이유 / API·DB·화면 영향 / 이행 방법 / 인수조건 / 검증 결과 / 배포 상태`

문서 초안은 현재 구현의 증거가 아니다. 테스트 fixture에서 통과한 AI/건강 데이터 수신을 실제 AI 정확도·실제 기기 자동 연동 완료로 기록하지 않는다. 계획 단계의 기능 버튼은 실행 가능한 것처럼 성공 표시하지 않고 필요한 선행조건을 보여준다.

## 필수 확인 사례

- 목적별 메뉴가 해당 항목만 저장하고, null/0·다른 날짜·다른 환자·취소·늦은 응답을 보존한다.
- 복약 일정 없는 환자, 복수 약·복수 회차, 같은 회차 수정, 일정 종료, 과거 날짜·미응답이 유지된다.
- 사진 미설정/전송 동의 없음/잘못된 이미지/제공자 실패/잘못된 JSON/낮은 확신/다른 환자의 초안/사진 교체/만료/중복 적용을 처리한다.
- 기기 batch 재전송·오래된 갱신·0/누락·삭제 반영·수동 보완 우선·연결 폐기·환자 간 토큰 오용을 검사한다.
- 실제 모바일 기기 권한 거절/철회/부분 허용/앱 종료/백그라운드 지연/휴대폰·워치 중복은 실제 기기 별도 검증표로 남긴다.
