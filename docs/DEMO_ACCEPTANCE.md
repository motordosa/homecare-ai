# 데모 사용·인수 확인 순서

공개 주소: https://homecare-ai-demo.onrender.com. 테스트는 가상 환자로 수행한다. 이 안내는 실제 배포/AI/기기 검증을 완료했다는 기록이 아니다. 수행 결과는 CHANGELOG에 대상 커밋·시간·환경과 함께 남긴다.

## 1. 새 버전 배포 확인

1. 보관할 기존 테스트 기록은 먼저 내보낸다. 무료 Render의 재배포는 DB/사진을 잃을 수 있으며 CSV는 전체 복원본이 아니다.
2. Render 서비스에서 **Manual Deploy → Deploy latest commit**을 실행한다.
3. `/api/health`에서 `ok:true`, `storage:"sqlite"`, `schemaVersion:2`를 확인한다. `npm run demo:check -- https://homecare-ai-demo.onrender.com`으로 해당 소스와 화면의 일치 여부도 확인한다. schema만으로 전체 배포 일치를 판단하지 않는다.

## 2. 메뉴·약별 복약

1. 의료진 웹에서 가상 환자를 선택하고 복약 메뉴에서 테스트 약명·1회량·오늘 시작·08:00/20:00 회차를 등록한다. 실제 처방을 입력하는 검사가 아니다.
2. 모바일 환자 웹에서 같은 환자의 복약 메뉴를 연다. 한 회차만 복용으로 저장하고 다른 회차는 미응답으로 남긴다.
3. 의료진 화면을 새로고침해 복용1회/미응답1회를 확인한다. 첫 회차를 미복용과 사유로 수정하고 수정 이력의 전후 상태를 확인한다.
4. 환자의 걸음 수 메뉴는 걸음 수만, 수면 메뉴는 수면만 입력하게 되는지 확인한다. 영양 카드는 식사 근거로 이동하고 화면 이동·뒤로가기·새로고침에서 선택 환자가 유지되는지 확인한다.

## 3. 사진 분석

키 없는 환경에서는 분석 불가 안내와 수동 저장이 정상 동작이다. 실제 분석은 Render 서버의 비밀 환경 변수 `HOMECARE_VISION_API_KEY` 및 `VISION_ENABLED=true` 설정이 필요하며 API 비용은 서버 무료 요금과 별도다.

- 식사: 먹기 전 전체 음식 사진 → 외부 전송 동의 → 분석 초안 → 식후 섭취비율/확인 → 저장 → 의료진 영양 추정과 출처 확인. 사진을 바꾼 뒤 이전 초안을 적용하지 못하는지도 확인한다.
- 약: 의료진 화면에서 글자가 읽히는 포장/약봉투 사진 → 후보 분석 → 원문 대조 → 이름/함량 입력 보조. 복용량·시간은 직접 확정한다. 알약 외형이나 사진 업로드만으로 복용을 확정하지 않는다.
- 실제 사진 검증은 음식/분량·제공자/모델·추정 오차를 별도 기록한다. fixture 테스트 결과를 실제 추론 정확도로 기록하지 않는다.

## 4. Android·갤럭시 워치

서버 새 버전과 Android 연결 앱이 모두 필요하다. [빌드·설치 및 기기 검증](../integrations/android/README.md)을 따른다.

1. 승인된 개발 검증용 휴대폰에서 삼성 헬스→Health Connect의 걸음/수면 공유를 확인한다.
2. 환자 웹의 건강 연결에서 Android 연결 코드를 만든다. 일회성 안내의 서버 주소·환자 이름·ID를 대조한다.
3. 앱에 서버 origin·정확한 환자 ID·토큰을 입력한다. 앱의 자료 주체 확인과 서버 사전 대조가 끝난 뒤 걸음/수면 읽기 권한을 허용한다.
4. 수동 동기화를 실행해 원기록과 웹의 날짜·걸음 수·실수면·출처·수신 시각을 대조한다. 자동 배경 동기화는 별도 권한/선택 후 지연·권한 철회·오프라인 검증을 수행한다.
5. 폰/워치 중복 합산, 자정 넘는 수면, 기록 수정/삭제, 미측정 null과 실제0, 수동 입력 우선순위를 확인한다. 기기 검증 전에는 자동 연동 완료로 표시하지 않는다.

공개 데모의 인증·동의·보관 체계가 실제 연구용으로 준비된 상태는 아니므로 실제 환자·연구 자료를 연결하지 않는다.
